# ONB-03.2 / ONB-03.3 — pacote para revisão independente

R2. Issue: fabiojuniort-cyber/tribusca-control#117. Sem merge, deploy, migration ou escrita em perfis produtivos.

## Contrato de cards por segmento

GET onboarding informa segmentCode e segmentLabel por atividade. O web agrupa atividades da empresa em um passo por segmento; escolhas e sugestões continuam restritas à unidade selecionada. Filial nova não herda escolhas da matriz. Nenhuma sugestão é confirmada automaticamente.

PUT onboarding aceita cardId segment:<código> e units [{establishmentId, conceptCodes, ncmCodes}], além de expectedVersion, releaseId e status. A lista precisa cobrir exatamente as unidades ativas com atividades naquele segmento, sem duplicações. Todos os itens são validados antes de uma única nova versão transacional do perfil. Tenant, OWNER/ADMIN, lock da empresa, lock compartilhado da publicação e comparação de versão permanecem obrigatórios. Uma tela antiga recebe 409; não há retry de escrita.

Estado anterior por CNAE continua legível e aceito pela API durante implantação backend → web. Um CNAE com múltiplos segmentos gera sugestões separadas por segmento. Na primeira gravação explícita, contribuições antigas por CNAE são repartidas entre os segmentos correspondentes; itens fora das sugestões são preservados na base manual. A confirmação substitui somente o segmento atual, mantendo outros segmentos, regime e demais dados do perfil. Não há backfill. Só ações explícitas do cliente escrevem.

## Interface

Popup de 800 px (responsivo), Inter, cantos 20 px, progresso azul, X no topo e rodapé fixo. Empresa → Estabelecimentos com IE manual → segmentos → resumo. Animação de seis segundos, frases do CSV a cada 2,5 segundos, fallback genérico. Lista inicial contém só sugestões publicadas da atividade/unidade, com oito linhas e expansão. Busca oferece até oito produtos e oito NCMs por código/descrição; não há lista integral do catálogo nem texto livre separado por vírgulas.

A tela antiga de Perfil Tributário foi removida do painel autenticado. Empresa e filiais ficam na mesma tela; o assistente é o único editor de escolhas. Dados cadastrais de identidade, endereço e CNAEs seguem as regras de proveniência: não se convertem em edição livre de dados oficiais. Correção inline da empresa permite razão social e Local Negócio; IE tem editor próprio no card.

## Versão do web e rascunhos

O build emite build-version.json com identidade do commit. Web consulta sem cache na entrada, foco e a cada 60 s, também antes de mutações. Deploy novo bloqueia novas mutações e apresenta: “Há uma versão nova do TriFaros. Recarregue a página para continuar.” 409 profile_version_conflict usa a mesma mensagem, sem código cru e sem retry.

Os rascunhos permanecem na memória da aba aberta, sem recarga automática. Recarregar ou fechar a aba descarta edições não salvas; o aviso orienta copiar antes. Falha de rede no probe não prova deploy novo e não remove a proteção de versão da API.

## IE e testes

PATCH state-registration faz comparação com o valor lido, restringe tenant/unidade/OWNER-ADMIN e não envia snapshot completo. Testes cobrem concorrência, no-op, limpeza e preservação integral dos perfis/CNAEs/outros campos.

A falha L11 da CI anterior vinha de um sufixo aleatório potencialmente só numérico interpretado como número de ato. A fixture agora tem prefixo alfabético; asserções originais mantidas.

Testes unitários do web cobrem agrupamento, escolha explícita, 409 com rascunho, filial vazia e aviso de bundle. Integração HTTP cobre atomicidade, unidades omitidas/duplicadas/estranhas e concorrência de segmento. Browser usa o bundle real com APIs controladas em ambiente descartável: fixture **AGREX — ambiente de teste**, CNPJ sintético, nove segmentos/doze passos, Arroz/NCM 1006 no CNAE 0111301, IE no popup, resumo/pulados, filial nova e aviso de versão. Capturas/vídeos não comprovam consulta RFB real ou readback produtivo; não usam dados privados de clientes.

## Gate

Executar CI completa nos dois HEADs e inspecionar evidências visuais. Revisão independente obrigatória; nenhuma autoaprovação. Ordem futura: backend → web. A API mantém contratos anteriores e OCC na janela; bundle antigo sem expectedVersion continua recusado. A correção não consegue acrescentar aviso retroativamente a JavaScript já carregado antes desta versão; essa primeira atualização ainda exige recarga do navegador.
